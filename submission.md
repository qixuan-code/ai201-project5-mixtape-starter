## Architecture at a glance

Three layers: `routes/` (HTTP), `services/` (business logic), `models.py` (data). Requests flow route → service → db.session/models → back up as a dict → `jsonify`. Nothing outside `services/` touches `db.session` directly except `routes/users.py`, which does one plain lookup (`db.session.get(User, user_id)`) instead of going through a service — the one place the pattern is broken.

## File-by-file

**`app.py`** — Flask application factory. Creates the single `db = SQLAlchemy()` instance used everywhere else, sets `SQLALCHEMY_DATABASE_URI` (defaults to `sqlite:///mixtape.db`, overridable via `DATABASE_URL` env var — note this resolves to `instance/mixtape.db` on disk, not the repo root), registers the four blueprints, and calls `db.create_all()` inside an app context. Tests override the URI to `sqlite:///:memory:` via the `config` param.

**`models.py`** — All 7 SQLAlchemy models plus 3 association tables. `User`, `Song`, `Tag`, `Playlist`, `ListeningEvent`, `Rating`, `Notification`. Ratings are their own table (`Rating`, one row per user/song pair, enforced by a `UniqueConstraint`) rather than a field on `Song` — so re-rating a song updates the existing row (`notification_service.rate_song` checks for an existing `Rating` before inserting). The association tables aren't plain many-to-many joins: `playlist_entries` carries `position` and `added_by`/`added_at` (so playlist order is explicit, not insertion order), and `friendships` is inserted twice per pair (once each direction) to make the relationship symmetric without a self-referential ORM trick. Every model has a hand-written `to_dict()` — that's the only serialization path; there's no schema/marshalling library.

**`routes/songs.py`** — `/songs` blueprint: search, get-by-id, rate, listen. Each handler parses `request.args`/`request.get_json()`, delegates to a service function, and maps `ValueError` → 400/404.

**`routes/playlists.py`** — `/playlists` blueprint: create playlist, get playlist metadata, list songs in a playlist, add a song to a playlist. The "add song" route calls `notification_service.add_to_playlist`, not `playlist_service` — the notification side effect lives with notifications, not playlists.

**`routes/users.py`** — `/users` blueprint: get user profile, get streak, list/mark-read notifications.

**`routes/feed.py`** — `/feed` blueprint: "listening now" (friends active in the last 24h) and general activity feed.

**`services/streak_service.py`** — `record_listening_event()` writes a `ListeningEvent` and calls `update_listening_streak()`, which is pure date-math on `user.last_listened_at` (same day → no-op, +1 day → increment, gap → reset to 1). `get_streak()` is a plain read.

**`services/feed_service.py`** — `get_friends_listening_now()` and `get_activity_feed()` both start from `user.friends` (via the `friendships` table) and query `ListeningEvent` for those friend IDs. Neither writes anything — the feed is entirely computed at read time from `ListeningEvent` rows; there's no separate feed table.

**`services/search_service.py`** — `search_songs()` does a case-insensitive `ilike` match on title/artist. `get_song()` is a plain lookup.

**`services/playlist_service.py`** — `create_playlist()`, `get_playlist()`, `get_playlist_songs()` (joins through `playlist_entries`, ordered by `position`), `get_user_playlists()`.

**`services/notification_service.py`** — `create_notification()` is the low-level insert; `add_to_playlist()` and `rate_song()` are the two callers that trigger it (see data flow below). `get_notifications()` / `mark_as_read()` are reads/updates for the notification inbox.

**`seed_data.py`** — standalone script (`python seed_data.py`), not imported by the app. Calls `create_app()` then `db.drop_all()`/`db.create_all()` itself, so it always starts from a clean schema. Seeds 5 users with real friendship rows, 10 tags, 13 songs split deliberately into 0-tag / 1-tag / 3-tag groups, a mix of recent (<30 min) and older (1–14 day) listening events, pre-set streaks, 3 playlists, and one notification. The comments in the file (e.g. "these expose Issue #3") make clear the seed data was built specifically to surface the bugs listed in the README's issue tracker.

**`tests/`** — one test file per service (`test_streaks.py`, `test_search.py`, `test_playlists.py`), each with its own `app` fixture on an in-memory SQLite DB. Tests call service functions directly, skipping routes entirely — routes are treated as too thin to need their own tests.

## Data flow #1: a friend rates a shared song → notification

1. `POST /songs/<song_id>/rate` hits `rate()` in `routes/songs.py`, which pulls `user_id`/`score` from the JSON body and calls `notification_service.rate_song(user_id, song_id, score)`.
2. `rate_song()` validates the score is 1–5, loads the `Song` and rating `User`, checks for an existing `Rating` row for that (user, song) pair (updates it in place if found, otherwise inserts a new one), commits, and returns the `Rating`.
3. **This is where Issue #4 lives**: `rate_song()` never calls `create_notification()`. Compare with `add_to_playlist()` in the same file, which — after appending the song to the playlist and committing — explicitly checks `song.shared_by != added_by_user_id` and calls `create_notification(user_id=song.shared_by, notification_type="song_added_to_playlist", body=...)`. `rate_song()` is missing the equivalent block, so the original sharer gets notified when someone adds their song to a playlist but not when someone rates it, even though both are "friend interacted with your song" events.
4. The route serializes whatever `rate_song()` returns via `.to_dict()` and responds `201`. Since no notification is created, nothing downstream (`get_notifications()` in `routes/users.py`) will ever surface it.

## Data flow #2: a user logs a listen → it surfaces in a friend's feed

1. `POST /songs/<song_id>/listen` → `routes/songs.py: listen()` → `streak_service.record_listening_event(user_id, song_id)`, which inserts a `ListeningEvent` row and updates the listener's streak, then commits.
2. Later, a friend hits `GET /feed/<user_id>/listening-now` → `routes/feed.py: listening_now()` → `feed_service.get_friends_listening_now(user_id)`, which reads `user.friends`, filters `ListeningEvent` to those friend IDs and a 24h cutoff, dedupes to one (most recent) event per friend, and builds `{friend, song, listened_at}` dicts.
3. No function directly connects steps 1 and 2 — the "feed" is a query, not a write path. Any `ListeningEvent` becomes feed-visible to friends automatically as soon as it's committed, until it ages out of the 24h window (or, in `get_activity_feed`, until it falls out of the most-recent-20).

## Patterns noticed

**Routes are pure translation layers.** Every handler in `routes/` does three things and nothing else: read the request, call exactly one service function, translate the result/exception into a JSON response. No handler builds a query or touches `db.session` (except the single exception in `routes/users.py: get_user()` noted above).

**Services own `db.session` and use `ValueError` as the error-signaling convention.** Every "not found" or "invalid input" case in a service raises `ValueError` with a message; every route catches `ValueError` and maps it to 400 or 404. There's no custom exception hierarchy — this one convention carries the whole error-handling story.

**The ORM layer never exposes SQLAlchemy objects past the service boundary.** Every service function that returns data to a route returns either a model's `.to_dict()` or a list of them (or the raw model, which the route then calls `.to_dict()` on) — routes never serialize fields manually, so JSON shape is defined once, in `models.py`.

**Association tables are used for anything relational needing metadata.** `friendships`, `song_tags`, and `playlist_entries` are all `db.Table()` objects rather than ORM association classes, which is why `playlist_entries` can carry `position`/`added_by`/`added_at` without a full model, but also why code that needs those extra columns (e.g. `playlist_service.get_playlist_songs`) has to query the table directly with `.join()` instead of just reading `playlist.songs`.

**Bugs are scoped one-per-service by design.** The README's issue tracker maps each of the 5 known bugs to exactly one service file (streak/feed/search/notification/playlist), and `seed_data.py`'s comments explicitly call out which seeded rows are meant to expose which issue (e.g., the 3-tag songs for the search duplication bug, the mixed recent/old listening events for the feed recency bug). The test suite mirrors this: one test file per service, each with an assertion commented with what the bug currently produces vs. what's expected (e.g. `test_playlists.py: assert len(songs) == 5  # Bug causes this to return 4`).

**Local imports avoid circularity.** `notification_service.add_to_playlist()` imports `Playlist` and `playlist_service.get_playlist_songs` inside the function body rather than at module level — `models.py` and every service import `db` from `app.py`, so top-level cross-imports between services would risk circular imports; the codebase resolves this ad hoc with local imports rather than a shared imports module.

## Root Cause Analysis

### Issue #5: The last song in a playlist never shows up

**How I reproduced it.** I seeded the DB (`python seed_data.py`), started the app, and picked a playlist ID: `sqlite3 instance/mixtape.db "SELECT id, name FROM playlist;"`. I then compared two counts for the same playlist: the raw row count in the join table, `sqlite3 instance/mixtape.db "SELECT COUNT(*) FROM playlist_entries WHERE playlist_id='<playlist_id>';"`, against what the API reported, `curl http://127.0.0.1:5000/playlists/<playlist_id>/songs`. The DB count was consistently one higher than the `count` field in the JSON response, and the missing song was always the one with the highest `position` value — confirming the bug is a dropped last item, not a random omission.

**How I found the root cause.** The README's issue table pointed directly at `playlist_service.py`, so I opened it and read `get_playlist_songs()` — the only function in that file that returns a song list. The query builds a join from `Song` to `playlist_entries`, filters by `playlist_id`, and orders by `position` ascending, which is correct: it retrieves every song in the right order. The moment I was confident I'd found the actual cause (not just a suspicious area) was the return line immediately below the query: `return [song.to_dict() for song in songs[:-1]]`. The query itself was already correct and fully tested by the ordering logic; the `[:-1]` slice was applied afterward, for no reason connected to the query or the docstring, which explicitly says "this function returns all songs in the playlist."

**The root cause.** `songs[:-1]` is a Python slice that returns every element except the last one. Because `songs` was already correctly ordered by ascending `position`, slicing off the last element always removes the song in the final playlist slot — regardless of playlist length, and even though that song has a completely valid `playlist_entries` row like every other song in the list. It's not a query bug or an off-by-one in the SQL ordering; it's a post-query truncation that has nothing to do with the rest of the function's logic.

**My fix and side-effect check.** I removed the slice so the function returns every song the query fetched: `return [song.to_dict() for song in songs]`. This fixes the root cause directly because the query was never the problem — once nothing truncates its output, all songs in position order are returned, including the last one. To check for side effects, I re-ran `tests/test_playlists.py`, which covers this exact function from three angles: `test_playlist_returns_all_songs` (asserts count == 5, previously failing at 4), `test_playlist_returns_songs_in_order` (asserts position ordering is preserved), and `test_empty_playlist_returns_empty_list` (asserts an empty playlist still returns `[]`, which is unaffected either way since slicing an empty list is a no-op). I also checked the only other caller of `get_playlist_songs` — `routes/playlists.py: get_songs()` — to confirm it just forwards the list and count with no logic of its own that assumed one song would be missing.

### Issue #1: My listening streak keeps resetting

**How I reproduced it.** `tests/test_streaks.py` already had a test aimed at this: `test_streak_increments_on_sunday`, which calls `update_listening_streak()` for a Saturday listen (streak → 1) and then a Sunday listen the next day, asserting the streak becomes 2 since the two listens are on consecutive calendar days. Running `pytest tests/test_streaks.py -v` failed on that test — the streak came back as 1 instead of 2, meaning a same-user, consecutive-day listen was being treated as a reset instead of an increment, but only when the second day was a Sunday (the equivalent Mon→Tue case in `test_streak_increments_on_consecutive_day` passed fine).

**How I found the root cause.** The README pointed at `streak_service.py`, and since the failing test was specifically about Sunday, I went straight to `update_listening_streak()` and read the branch that decides between incrementing and resetting. The three branches are `days_since_last == 0` (no-op), an `elif` for the increment case, and an `else` that resets to 1. The `elif` read `days_since_last == 1 and today.weekday() != 6`. I checked what `datetime.weekday()` actually returns — Monday is 0, Sunday is 6 — and confirmed that was the exact reason the Saturday→Sunday test failed: on a Sunday, `today.weekday() != 6` is `False`, so the `elif` as a whole is `False` even though `days_since_last == 1` is `True`, and execution falls through to the `else` reset branch.

**The root cause.** The increment condition required two things to be true: consecutive-day listening (`days_since_last == 1`) *and* today not being a Sunday (`today.weekday() != 6`). That second clause has no basis in the stated streak rules ("increments by 1" on any consecutive day) — it isn't gating a real edge case, it's an unconditional exception that fires every single week. So any user whose consecutive-day streak happened to land on a Sunday had it silently reset to 1 that day, which is exactly the "streak keeps resetting" symptom, recurring weekly regardless of how consistently the user actually listened.

**My fix and side-effect check.** I removed the `and today.weekday() != 6` clause, leaving `elif days_since_last == 1: user.listening_streak += 1`, so any consecutive-day listen increments regardless of weekday. This fixes the root cause directly because the reset branch is now only reached when `days_since_last` is actually 0 (handled separately, above) or greater than 1 — i.e., an actual gap — never because of which day of the week it is. To check for side effects, I ran the full `tests/test_streaks.py` suite, not just the Sunday test: `test_streak_starts_at_1_for_new_user`, `test_streak_increments_on_consecutive_day`, `test_streak_does_not_double_count_same_day`, and `test_streak_resets_after_skipped_day` all still pass, since none of them depend on the weekday at all — confirming the fix only changes behavior on the one day it was wrong for, and doesn't touch the no-change or real-reset paths.

### Issue #4: I got notified when a friend added my song to a playlist but not when they rated it

**How I reproduced it.** I compared the two "friend interacted with your song" paths side by side. `POST /playlists/<id>/songs` (adding a song to a playlist) followed by `GET /users/<sharer_id>/notifications` produced a `"song_added_to_playlist"` entry as expected. Running the equivalent for ratings — `POST /songs/<song_id>/rate` with a `user_id` different from the song's `shared_by`, then checking `GET /users/<shared_by_id>/notifications` — produced no new notification at all, confirming the rating path silently does nothing on the notification side while the playlist path does.

**How I found the root cause.** Both `add_to_playlist()` and `rate_song()` live in `services/notification_service.py`, so I read them side by side. `add_to_playlist()` ends with a check, `if song.shared_by != added_by_user_id: create_notification(...)`, right after committing the playlist change. `rate_song()` also loads the `song` and the rating `User` (as `rater`), and also commits a change (`db.session.commit()`), but its function body ends immediately after that commit with `return rating` — there is no call to `create_notification()` anywhere in the function. Since this file is literally where `create_notification()` is defined and where the playlist path already calls it, finding that `rate_song()` never calls it at all (not a broken call, an absent one) was the specific cause, not just a suspicious area.

**The root cause.** `rate_song()` is missing a step, not misconfiguring one: after saving a `Rating` row, it never calls `create_notification()` for the song's sharer. `add_to_playlist()` treats "friend acted on your shared song" as notification-worthy and implements that; `rate_song()` performs the equivalent action (a friend acting on your shared song) but the code path for turning that into a notification simply doesn't exist in the function. There's no faulty condition to fix — the fix is additive.

**My fix and side-effect check.** I added the missing block at the end of `rate_song()`, mirroring `add_to_playlist()`'s pattern exactly: after `db.session.commit()`, `if song.shared_by != user_id: create_notification(user_id=song.shared_by, notification_type="song_rated", body=f"{rater.username} rated your song '{song.title}' {score}/5.")`, reusing the `song` and `rater` objects already loaded earlier in the function rather than re-querying, then `return rating` unchanged at the end. I verified this manually against the seeded DB: rating a song as a user other than its `shared_by` produced a new `"song_rated"` notification when checked via `GET /users/<shared_by_id>/notifications`; rating the same song again with a different score produced another notification (the fix notifies on every rate call, including re-rates, matching `add_to_playlist`'s level of simplicity rather than adding first-rating-only dedup logic); and having the song's own sharer rate their own song produced no new notification, confirming the `song.shared_by != user_id` guard. I also re-checked `add_to_playlist()` itself to make sure adding this block to `rate_song()` didn't require any shared-state changes — the two functions don't share any local variables or side effects, so this was a pure addition with no risk to the playlist-notification path.
